## Решение в двух строках

*Исходная постановка 17 ноября 2026 года. Часть пунктов изменена решением [0013](../decisions/0013-voice-note-integration.md): единый плагин Hermes Desktop на штатном Desktop Plugin SDK, очередь заданий; CLI и MCP остаются входами. Пометки в требованиях — `REQUIREMENTS.md`, раздел 10.*

Отдельный Python CLI + локальный MCP stdio, без форка Hermes и нового UI. Переиспользовать имеющиеся ASR/акустические проверки и добавить один действительно работающий audio-understanding backend — только после короткого capability gate.

Сначала доказать, что модель различает особенности русской речи по звуку, затем делать полноценную упаковку. Красивый JSON с пересказом текста не проходит приёмку.

## Что необходимо решить до исполнения

*Исторический перечень на 17 ноября 2026 года. Где эти решения приняты и что остаётся открытым — [ACCEPTANCE](../ACCEPTANCE.md) и доска проекта.*

1. Явное поручение на реализацию и целевой каталог отдельного проекта. Публикация remote не подразумевается.
2. После короткого сравнения кандидатов: локальный либо согласованный внешний backend, ресурсный/денежный бюджет и доступные разрешения.
3. Независимый размеченный материал и заранее принятый протокол качества. Пороги в ТЗ — инженерное предложение; на малом пилоте нельзя обещать универсальную точность.
4. После готовности standalone pipeline: отдельное разрешение на подключение к действующему Hermes.

Не требуется решать всё сразу. Агент может начать разрешённую разведку без inference и предложить конкретный backend/бюджет перед установкой или отправкой записей. Весь проект нельзя назвать законченным, пока аудиоспособность, русская квалификация и интеграция остаются непроверенными.

## Локальный handoff — не публиковать без очистки

## Локальный handoff

В исходном пакете этот раздел перечислял абсолютные пути рабочей станции к уже существующему акустическому/ASR-слою и development-записям. Перед публикацией репозитория раздел вынесен в `local/HANDOFF.md`, который не входит в git (см. `.gitignore`): пути относятся к одной машине, не являются production dependencies и не входят в публичные fixtures. Агент на этой машине читает `local/HANDOFF.md`, когда задача ссылается на существующий слой; на другой машине файла нет, и такие задачи заканчиваются статусом «ждёт владельца».

Из-за этой правки SHA-256 файла `README.md` в `VERIFICATION.json` не совпадает с опубликованной версией; хеши трёх остальных документов совпадают.


## Статус проверки документов

При сборке проверить наличие четырёх Markdown-файлов, уникальность и диапазоны R/T IDs, существование локальных handoff путей, согласованность имён интерфейсов, целостность ZIP и отсутствие аудио/секретов среди вложений. Эти проверки подтверждают пригодность пакета к передаче, не работоспособность будущего инструмента.
