# Speech Review — требования к инструменту

Статус: проект требований для отдельного репозитория; реализация и модель не выбраны. Подготовлено 17 ноября 2026 года. Это не разрешение устанавливать модели, передавать записи провайдерам, публиковать репозиторий или менять действующий Hermes.

## 1. Цель и пользовательский сценарий

Пользователь записывает голосовое в существующем интерфейсе Hermes. Агент получает инструмент, который возвращает проверяемые наблюдения о звучании русской речи, а не только текст. Агент использует результат для речевых упражнений, разбора свободного рассказа, чтения и сопоставления исходной/контрольной попыток.

Главная проблема: существующие ASR и акустические метрики не дают текстовому агенту непосредственного восприятия звука. Поэтому продукт обязан добавить backend, который реально получает аудиосигнал. Обёртка над Whisper, текстовый LLM с расшифровкой или спектрограмма не закрывают эту задачу.

Обещание продукта: «анализ звучания аудиомоделью с указанием фрагментов и ограничений». Не «человек прослушал», не «Hermes сам услышал», если это не соответствует выполненному маршруту. Модельное наблюдение не становится достоверным фактом от наличия уверенного текста.

Пользовательский результат: до трёх приоритетных наблюдений, конкретные таймкоды/клипы, объяснение влияния на понятность и одно посильное контрольное задание. Полный список существенных замечаний сохраняется в отчёте; ограничение краткого ответа не скрывает их.

## 2. Минимальная архитектура

Предлагаемый репозиторий: `speech-review` — рабочее имя, не созданный GitHub-проект.

```text
Вложение в Hermes
  → локальный MCP stdio на хосте, где лежит вложение
  → тот же Python application layer, который вызывается CLI
      → проверка входа и подготовка неизменённой временной шкалы
      → локальный ASR + акустические измерения
      → ОДИН выбранный audio-understanding backend
      → валидатор наблюдений, клипы, JSON + Markdown
  → Hermes: краткий разбор и контрольная попытка
```

- Сначала Linux backend и имеющийся сценарий загрузки WAV. Windows-клиент продолжает отправлять вложения существующим способом; Windows-исполнение анализатора не входит в первую приёмку.
- Никакого форка Hermes, новой кнопки записи, собственного чата или сервиса загрузки в первой версии. **Изменено решением 0013 (§10):** кнопка записи и приём записи на анализ — через штатный Desktop Plugin SDK; запрет форка, второго клиента и собственного чата сохраняется.
- Python-пакет с CLI; тонкий MCP-адаптер использует те же функции, не второй pipeline. Отдельная среда и lockfile; runtime Hermes не модифицировать.
- Локальный stdio выбран вместо HTTP: первая версия не открывает сетевой порт и не требует отдельного web API. **Изменено решением 0013 (§10):** маршруты `/api/plugins/sound-scout/` внутри существующего gateway Hermes; новых портов нет. Поддержка Hermes подтверждается официальными материалами H1/H2 ниже.
- Один backend после исследовательского допуска. Не строить универсальный каталог моделей. Если выбран облачный backend, он явный opt-in, а не fallback при неудаче локального.
- Один анализ одновременно. В первой версии нет очереди заданий, Redis, БД и фонового распределённого исполнения. **Изменено решением 0013 (§10):** файловая очередь заданий и один фоновый runner; тяжёлый анализ по-прежнему по одному; Redis, БД и распределённого исполнения нет.

## 3. Функциональные требования

### R01 — честная доступность

`doctor` / `speech_capabilities` отдельно возвращает состояние декодера, ASR, акустического анализа и audio-understanding: `ready`, `unavailable`, `unvalidated`, `permission_required` с причиной. Установка Python-пакета и наличие весов не равны успешному inference. `ready` требует сохранённого успешного smoke-test для текущих model/revision/config/environment; без него — `unvalidated`. Показывать время и fingerprint последней проверки; смена соответствующих компонентов делает её устаревшей. Это не гарантия доступности следующего вызова. Doctor только читает состояние: не скачивает модели, не вызывает inference и не отправляет файлы.

Квалификация качества отдельно: `validated_ru` истинно только при прохождении принятых порогов и дикции, и просодии на зафиксированной held-out части. Хранить также `diction_validated_ru` и `prosody_validated_ru`; не скрывать непрошедшую способность за общим smoke-test. Не брать эти значения из рекламы модели.

### R02 — вход и сохранность

MVP: WAV PCM, MP3, OGG/Opus, M4A/AAC, один аудиопоток, один основной говорящий, русский язык. Сначала обязательный WAV happy path, остальные заявленные форматы закрыть отдельными декодируемыми fixtures до объявления всей версии готовой.

Предлагаемые границы версии: до 180 секунд и 100 MiB входного файла, не больше двух каналов. Это инженерный лимит, не речевая норма. Проверять размер контейнера, заявленные параметры и реальный объём/длительность декодированных данных. Сверх лимита — явный отказ, не скрытое усечение. Смешанную речь/несколько говорящих считать неподдержанным или ограничивающим анализ условием; надёжное распознавание количества людей не заявлять без проверки.

Оригинал read-only, SHA-256, метаданные и source ID. Производные — в отдельном run-каталоге. Выбор канала фиксировать; один пустой канал не усреднять с рабочим. Дублированное стерео не считать двумя говорящими. Не удалять паузы и не улучшать звук скрыто. Для прослушивания допустима отдельная линейно усиленная копия с записанным gain; измерения относятся к исходному сигналу.

### R03 — реальные аудиовходы

Audio backend должен получать байты/PCM аудио, а не только транскрипт. Сохранять проверяемую запись маршрута: backend/model/revision, длительность и хеш фактически переданного audio payload, preprocessing, диапазоны источника, версия prompt, настройки inference, request ID при наличии. Утверждение модели «я прослушала» не доказательство маршрута.

Первый проход audio review — без готового транскрипта и эталонного текста, чтобы уменьшить подсказку ожидаемых слов. Если отдельный второй проход получает текст, сохранять его как text-assisted и не заменять им слепой результат. Чтение эталона не доказывает его точное произнесение. Дополнительный модельный проход входит в согласованный лимит, не запускается автоматически за деньги.

Весь заявленный анализируемый диапазон должен быть передан audio backend. При chunking сохранять offsets, overlaps, объединять дубли и отмечать пограничные ошибки. При выборочной проверке перечислять reviewed/unreviewed ranges; не выдавать несколько клипов за прослушивание полной записи.

### R04 — четыре независимых слоя

1. **Содержание:** ASR, выполнение задания, связность, точность ответа. Текстовый анализ разрешён, но подписан.
2. **Измерения:** длительность, каналы, уровень, обнаруженные речевые интервалы, F0/RMS с параметрами и ограничениями. VAD-разрыв не равен оговорке, F0 не равен выразительности.
3. **Звучание:** разборчивость конкретных слов/окончаний, произнесённые повторы и самокоррекции, границы фраз, смысловой акцент, функциональность пауз. Это наблюдения audio backend, отдельно от цифр и транскрипта.
4. **Тренерская рекомендация:** конкретное небольшое действие, привязанное к наблюдению и цели упражнения. Не диагноз и не переписывание личного сообщения за пользователя.

Не оценивать эмоции, личность, здоровье, «уверенность в себе», привлекательность и харизму по голосу. Не требовать сценической экспрессии от спокойной бытовой речи. Не считать акцент или необычное имя дефектом без установленной проблемы понимания.

### R05 — каждое замечание имеет основание

Обязательны: категория, конкретное наблюдение, интервал на исходной шкале, ссылка/ID воспроизводимого клипа, основание, влияние на понятность, неопределённость и короткое действие для проверки/исправления.

Развести `measurement`, `transcript`, `audio_model_observation`, `human_verified`. Последний источник — только отдельная подлинная человеческая разметка, не самоназвание модели. При разногласии ASR и аудиомодели хранить обе версии; не выбирать автоматически более литературную. Нет принудительного требования найти дефект. Положительное заключение также ограничено реальным охватом.

Калиброванную вероятность ошибки не придумывать. Словесная уверенность модели не превращается в процент. Любое сомнительное слово помечается `uncertain`, а не записывается пользователю как оговорка. `not_assessed` не равно «всё хорошо».

### R06 — выразительность в контексте

Оценивать не «эмоциональность вообще», а наблюдаемую функцию: различим ли акцент, помогает ли пауза членению, не разрывается ли существенная связь, завершена ли фраза. Если намерение говорящего неизвестно, не объявлять интонацию неверной; можно описать услышанное выделение и спросить о намерении.

Изменения высоты/уровня и оценки аудиомодели хранить раздельно. Не выдавать низкий диапазон F0 за монотонность, длинную паузу за тревогу, тихую запись за неуверенность. Предлагаемые корректировки не требуют крика, искусственного понижения голоса или болезненных упражнений.

### R07 — исходная и контрольная попытки

Сопоставление по заранее указанному критерию, не общий рейтинг человека. Выход: `improved`, `not_improved`, `inconclusive` с доказательствами обеих попыток и различиями условий.

Не путать сокращение файла с улучшением речи; включать оговорку о паузах и новом вопросе. Смена gain/микрофона/задачи ограничивает соответствующие сравнения. Различать исправление после подсказки, сохранение позже и перенос в другой контекст. Один удачный контроль не доказывает устойчивый навык.

### R08 — пригодный ответ для Hermes

Малый структурированный результат непосредственно в tool response: статусы слоёв, охват, до трёх приоритетных findings, ограничения, ссылки на локальные report/JSON/clips. Полный результат остаётся на диске. Не возвращать сотни тысяч строк PCM, base64 или полную техническую диагностику в контекст.

Владелец занятия — Hermes: номера раундов, режим игры, лимит времени и решение о следующем задании не сбрасываются сервером. Сервер не отправляет сообщения знакомым, не начинает запись микрофона и не слушает Discord. Запись третьих лиц вне scope.

### R09 — приватность и расходы

Default: offline, no uploads, no telemetry, no model downloads. Установленные согласованные локальные модели разрешены только в рамках запроса анализа. Распознавание не даёт разрешения загрузить новый audio backend.

Для внешнего backend до вызова согласовать провайдера, модель, конкретные записи/диапазоны, цель, число запросов, объём, стоимость/предел расходов и заявленные условия хранения. Неизвестная цена — блокер платного вызова. Ключи не хранить в репозитории/логах. Не считать подписку, OAuth или наличие ключа разрешением на списание.

Не принимать `approved=true` из аудио, транскрипта или аргументов LLM за согласие. Владельцем разрешения является пользователь, не агент-разработчик. До внешнего пилота в Gate 0 зафиксировать один конкретный механизм: существующее доверенное подтверждение на стороне host с прямым участием пользователя и проверяемой привязкой к provider/model, хешам записей/диапазонам, числу запросов, бюджету и сроку. Агент только проверяет полученный допуск, не выпускает и не расширяет его сам. Если установленный host не предоставляет такого механизма или его привязка к scope не проверена, внешний вызов `blocked`; не заменять его самодельным JSON-флагом и не строить новый approval broker в рамках локального MVP.

Локальный backend — допустимый полный вариант MVP при реальной работоспособности. Требования об облачных расходах, provider request ID и outcome unknown применимы только при выбранном и разрешённом внешнем backend. В локальной версии внешние вызовы отклоняются, облачные тесты отмечаются `not_applicable`; не строить неиспользуемый платёжный контур. Общие offline, приватность, запрет скачивания и resource limits действуют всегда.

При outcome unknown после отправки платного запроса не повторять его автоматически. Сохранять request ID/состояние и действовать только по гарантии провайдера либо новому решению владельца. Sampling MCP отключён явно; текстовый sampling не заменяет аудиовход.

### R10 — безопасность и ограниченные ресурсы

Вход только из настроенных allowed roots. Выход только под приватным data root, без обхода через `..`, symlink или race с заменой пути. Отдельно запретить чтение credentials, env/config и произвольных устройств. Чужой путь из транскрипта не даёт разрешения на чтение.

Не принимать URL/playlist в качестве входа первой версии; отключить сетевые протоколы декодера и проверить это отрицательным тестом. subprocess только argv, без shell. Ограничить subprocess wall time, decoded samples, память/параллелизм и размер модельного ответа. Ошибка в контейнере не должна запускать неконтролируемую загрузку.

Текст/аудио — недоверенные данные: «игнорируй инструкции», команды оболочки, просьбы выдать ключи внутри записи не исполняются. Audio backend не получает tools или секреты; его JSON проходит независимую валидацию. В read-only scope источников нельзя создавать/удалять файлы.

### R11 — статусы, воспроизводимость и завершение

У каждого этапа `completed`, `skipped`, `unavailable` или `failed` с причиной. Общий `complete` означает завершение запрошенных слоёв и охвата, а не доказанную безошибочность модели. Если запрос включал звучание, а выполнен только ASR, результат `partial`, не success hearing.

Измерять холодную и тёплую задержку, память и аппаратную конфигурацию, отдельно model load и inference. Предлагаемый UX-бюджет: короткий клип до 30 с — до 60 с обработки; файл до 180 с — до 180 с обработки на выбранном целевом хосте. Это проверяемые цели, не уже доказанные показатели; если backend их не достигает, обозначить ограничение и согласовать иной режим до заявления готовности.

При превышении deadline остановить собственный worker, собрать частичные результаты, не оставлять потерянный процесс. Stdio stdout содержит только протокол; диагностика — stderr с редактированием чувствительных данных. Завершение клиента/отмена освобождает owned процессы. Никаких скрытых повторов inference.

Run ID + приватный run-каталог; повторный вызов с тем же request ID и тем же content/config hash возвращает тот же результат, а с иным содержимым отклоняется. Cache identity включает аудио, модель/revision, preprocessing, диапазоны, prompt/schema и контекст задачи. Ошибки и outcome unknown не являются разрешением повторно списывать запрос.

### R12 — интеграция и переносимость

MCP инструменты: `speech_capabilities`, `speech_analyze`, `speech_compare`. CLI операции: `doctor`, `analyze`, `compare`, `serve`. Это проектируемые имена, не существующие команды.

CLI/MCP используют один валидатор и application layer. Параметры модели, budgets, allowed roots и data root задаются оператором, не произвольными shell-аргументами из LLM.

Команда stdio запускается на хосте backend, где уже лежит вложение. Не пытаться открыть Windows-путь на Linux. Не переносить логические пути приватных записей в публичную конфигурацию. В пакете интеграции: README установки, пример настроек, короткий Hermes skill о корректной трактовке результата. Не вносить код в ядро Hermes и не делать Desktop plugin. **Изменено решением 0013 (§10):** Desktop plugin разрешён только на штатном Desktop Plugin SDK; код в ядро Hermes по-прежнему не вносится.

Подключение к действующему профилю — отдельно согласованное действие. Через управляющий инструмент MCP/поддерживаемый flow установленного host, без ручного редактирования `mcp_servers` и обхода ограничений. Явно указать tool allowlist, `sampling.enabled=false`, `supports_parallel_tool_calls=false`, `connect_timeout` и `timeout`. Не полагаться на значения по умолчанию: в проверенных официальных примерах и таблицах timeout различается. Внешний timeout должен оставлять запас над worker deadline.

После подключения: readback exact entry, discovery в нужном runtime, реальный вызов из новой/согласованно обновлённой сессии Hermes. Прямой SDK-вызов не равен доказанному native tool exposure. Анализ создаёт локальные артефакты — не помечать его read-only только ради обхода approvals; metadata/annotations должны соответствовать фактическим побочным эффектам.

## 4. Контракт результата версии 1

Реализовать JSON Schema и её проверки до backend. Ниже перечень обязательных частей, не пример якобы выполненного анализа:

- `schema_version`, `request_id`, `run_id`, `status` (`complete|partial|blocked|failed`).
- `source`: ID, SHA, фактическая длительность, каналы; путь только в локальном отчёте/разрешённом ответе.
- `capabilities`: фактически доступные слои и `validated_ru` выбранного audio backend.
- `stages`: статусы подготовки, ASR, акустики, audio review и отчёта.
- `coverage`: requested/reviewed/unreviewed ranges на исходной шкале времени.
- `provenance`: версии, input modalities, audio payload SHA, prompt/schema SHA, преобразования и ограничения.
- `transcript`: raw artifact reference; исправления отдельным слоем, не перепись raw.
- `measurements`: именованные единицы, методы, настройки; неполученные значения null, без NaN/Infinity.
- `findings`: ID, category, observation, start/end, evidence_basis, evidence_refs, confidence_note, impact, correction; положительные/нейтральные/отрицательные наблюдения без обязательной квоты.
- `assessment_status`: отдельно diction/prosody/content; `not_assessed` с причиной.
- `artifacts`: компактные ссылки на report, JSON, клипы с точным отображением на оригинал.
- `limits`, `errors`, `cost`: фактическое/оценочное/unknown; не придумывать нулевую стоимость облачного ответа.

Сервер, не модель, выставляет provenance, stage status, trusted evidence types и стоимость. Валидировать порядок/границы таймкодов, existence/hash evidence, уникальность finding ID, соответствие review coverage. Запретить human_verified без человеческого evidence record. Текстовая модель не может сама повысить transcript evidence до audio_model_observation.

## 5. Приёмка и этапы

### Gate 0 — доказать недостающую способность до большой обвязки

Сравнить не больше двух реалистичных кандидатов по официальным первичным источникам: аудиовход, русский, реальные задачи дикции/просодии, лицензия, доступ, память/задержка, стоимость и приватность. Поддержка русского ASR не доказывает русскую оценку произношения. Не фиксировать «лучший» backend без реального согласованного пилота.

Первый разрешённый spike: один выбранный backend, реальные короткие записи с одним и тем же текстом, но разным смысловым акцентом/произнесением. Нужен протокол фактического audio input и отличие от transcript-only baseline. Если backend даёт только пересказ или не работает на русском, результат NOT READY; не продолжать упаковку такого результата как готовой слуховой проверки.

### Gate 1 — утвердить протокол и границы приёмки

До полноценной реализации утвердить корпус/разметку, разбиение development/held-out, пороги, процедуру сопоставления событий и разрешения. Перечень T01–T10 ниже — сквозная матрица проверок, НЕ требование построить весь продукт до Gate 2. Проверки выполнять по мере появления соответствующего слоя; окончательная приёмка — Gate 3. Короткий capability spike Gate 0 не равен полной квалификации. Разделить готовность standalone инструмента и разрешение/факт подключения к Hermes.

#### Сквозная матрица проверок

T01. Оригинал неизменён, неверный/слишком большой/слишком длинный/повреждённый вход отклоняется; нет автоматического URL-fetch.

T02. Проверены active+silent channel, duplicated stereo, zero signal и cancellation; шкала времени и offsets сохраняются.

T03. Trace доказывает подачу реальных audio bytes/PCM; пустой/отсутствующий аудиовход не принимается как успешный audio review. Transcript-only negative control не получает слуховой статус.

T04. Различение звучания квалифицировано на заранее размеченных русских фрагментах: произношение, повтор/самокоррекция, смысловой акцент, членение паузами. Нужны также чистые записи, редкие имена, фоновые помехи и неоднозначные случаи, где следует воздержаться.

T05. На зафиксированных отрицательных контролях (тишина, шум, специально испорченный ASR) при выбранных настройках — ноль уверенных выдуманных реплик или дефектов произношения. Конечная проверка не обещает этого для произвольного будущего аудио. Известный правильный текст не подменяет реальную запись. Согласие двух распознавателей не считается ground truth. Уверенность текста ASR на контролях определяется правилом `suspect_hallucination`, а не вероятностями слов (`docs/decisions/0005-asr-silence-hallucination.md`).

T06. Для квалификационного набора предлагается минимум 20 отдельных клипов, включая не менее 5 отрицательных контролей. До пилота отдельно зафиксировать held-out manifest и достаточное число размеченных событий ДЛЯ КАЖДОЙ заявленной категории; начальное предложение — минимум 5 отчётливых событий дикции и 5 просодии именно в held-out части, плюс отрицательные контроли и хотя бы две пары с одинаковыми словами и разным акцентом. Один клип может содержать несколько категорий, но варианты одного исходника/одной парной записи не разносить между development и held-out. Непредставленная категория не проходит квалификацию. Разметка сделана человеком независимо от выходов модели; неоднозначные случаи отдельно, не принудительно верные/неверные. Для спорной просодии — второе слушательское мнение либо метка uncertain.

Порог пилота фиксировать ДО просмотра тестовых результатов: предлагаемые инженерные цели — precision замечаний не ниже 0.80, recall заранее размеченных отчётливых событий не ниже 0.70 ОТДЕЛЬНО для дикции и для просодии на held-out части; запрещены уверенные выдуманные высказывания на зафиксированных отрицательных контролях. Интервал finding должен покрывать размеченное событие, а не всё аудио; допустимые границы/overlap matching заранее определить для каждой категории. Отдельно показать результаты дикции и просодии, число событий и abstention, не прятать провал одной категории в общей средней. Это малый пилот, не статистическое доказательство качества для всех людей; пороги и минимальные объёмы — предложение владельцу, не медицинские нормы. Если проверено только одно направление, сообщить его отдельный статус; общий `validated_ru` остаётся false.

Для независимой проверки удержать часть материала от настройки prompt/модели; если доступен только development-набор, честно NOT QUALIFIED. Полный отказ от замечаний не проходит recall. Подмена неизвестной разметки выдуманной запрещена. До подтверждения тестового протокола разрешены инженерные тесты, но качество не объявляется принятым.

T07. Нет сети/download/upload без политики; инструкция внутри аудио не может вызвать tools, прочитать секрет или изменить approval. Защита путей, URL/playlist, разрешений файлов и логов проверена отрицательными тестами.

T08. Проверены timeout/cancel, malformed model JSON, частичный backend failure, duplicated request ID и mismatch request payload. Для выбранного внешнего backend дополнительно проверен outcome unknown без автоматического повторного платного вызова; для local-only эта часть `not_applicable`. Worker освобождён; частичный отчёт не назван complete.

T09. Два отдельных результата: (a) standalone CLI и MCP stdio проходят одинаковый локальный happy path, schema/интервалы/артефакты согласуются; (b) после отдельного разрешения получен реальный native Hermes вызов и readback регистрации. Отсутствие разрешения блокирует (b), не отменяет успешный (a), но не даёт объявить интеграцию законченной. Моки подтверждают контракт, но не способность аудиомодели и не подключение Hermes.

T10. Сопоставление двух реальных записей привязано к выбранному критерию, сохраняет различия условий; отсутствие данных возвращает inconclusive. Чистая установка, pinned environment/model receipt и отсутствие приватных данных в Git проверены. Нельзя объявить готовность только по unit tests и красиво заполненному JSON.

### Gate 2 — реализация минимального вертикального сценария

Вход WAV → подготовка → существующий ASR/акустический слой → один настоящий audio backend → доказательства/клипы → report → CLI → MCP → Hermes после разрешения. Начинать с этого пути, не с UI и абстракций для пяти провайдеров.

### Gate 3 — итог статусов

Отдельно принять: инженерные тесты; квалификацию русского audio review; реальные CLI/MCP; фактическое подключение Hermes. При отсутствии согласия на модель/данные/подключение обозначить конкретный blocked stage, не считать весь продукт готовым и не запускать запрещённое.

## 6. Что переиспользовать

Существующий локальный акустический слой: функции `channel_report`, `choose_mono`, `acoustic_track`, `speech_activity`, `analyze_file`, тесты каналов/численных границ. ASR-процедура: CPU/int8 Whisper, передача проверенного float32-массива после системного FFmpeg, raw outputs, local_files_only, сетевой запрет; сегменты с `suspect_hallucination` считаются недоверенным текстом (`docs/decisions/0005-asr-silence-hallucination.md`). Не переписывать проверенные алгоритмы без причины.

Перед переносом прочитать исходники/тесты, проверить происхождение и лицензии. Не зависеть в новом пакете от абсолютного пользовательского пути и не делать exec/read_text старых одноразовых скриптов production-архитектурой. Вынести минимально необходимую логику с сохранением проверок, а не копировать всю папку с приватными отчётами.

Пять записей первого дня — development-примеры, уже использованные в разговоре, не независимый слепой тест и не эталон дикции. В открытый репозиторий их не включать. Частные пути и hashes относятся к локальному handoff, не к универсальным fixtures.

## 7. Не входит в MVP

Live Discord bot, непрерывная запись, diarization, распознавание личности, медицинская диагностика, автоматическая оценка привлекательности/эмоций, цифровой балл харизмы, новый Desktop recorder, web dashboard, векторная БД, подписки, обучение собственной модели, массовый импорт переписок и аудио. Не добавлять их «для будущего».

## 9. Выбранный audio-understanding backend и учёт зависимостей

Внесено 18 ноября 2026 года по прямому поручению владельца. Заменяет раздел «Рекомендация» в `docs/decisions/0001-audio-backend.md` от 17 ноября.

**Бюджет ресурсов (решение владельца):** не больше 20 GB оперативной памяти и 12–16 GB видеопамяти; предпочтение открытым и лёгким моделям. Первая версия запускается на станции разработки: только CPU, без дискретного GPU.

**Backend:** Gemma 4 E4B-it (Google, Apache-2.0), GGUF из `ggml-org/gemma-4-E4B-it-GGUF` ревизии `8903cb408c7df39cde2ed15fac397e6d7be92951`: языковая модель `gemma-4-E4B-it-Q8_0.gguf` и аудиопроектор `mmproj-gemma-4-E4B-it-BF16.gguf` (≈ 9,0 GB вместе). Runtime — llama.cpp v1.0.0, сборка `b12359`, CPU x64, локальные `-m`/`--mmproj`, без загрузки из сети при запуске. Точные размеры, SHA-256 и каталоги — `docs/dependencies.md` раздел 3.

**Что это решение не меняет:**

- Gate 0 остаётся обязательным: Gemma 4 E4B-it выбрана для spike, а не признана способной. Если spike даёт NOT READY (модель пересказывает текст, не различает пары с одинаковыми словами и разным звучанием, выдумывает на отрицательных контролях), backend не упаковывается, а замену выбирает владелец. Запасной кандидат — Borealis-5b-it (Vikhrmodels, Apache-2.0), вне бюджета — GigaChat3.1-Audio-10B-A1.8B (≈ 22,5 GB в bf16) и Qwen3-Omni-30B-A3B.
- Свидетельств оценки русского произношения и просодии у выбранной модели в первичных источниках нет; есть русский ASR и перевод. `validated_ru` выставляется только по Gate 1.
- R09: никаких внешних вызовов, загрузок при работе инструмента и телеметрии. Загружены только перечисленные файлы, по разрешению владельца от 18 ноября 2026 года.

**Ограничения модели, обязательные для реализации:** один аудиовход не длиннее 30 с, 16 kHz mono; длинная запись режется на клипы ≤ 30 с по речевым интервалам с пересчётом offsets на исходную шкалу (R03); модель не выдаёт таймкодов, поэтому локализация строится по границам клипа, а наблюдение без локализации остаётся `unlocalized` (R05).

**Учёт зависимостей:** каждый Python-пакет, системная программа, runtime и файл весов, от которого зависит инструмент, записан в `docs/dependencies.md` с версией или ревизией, источником, лицензией и, для бинарей и весов, SHA-256. Новая или обновлённая зависимость вносится туда в том же коммите. Скачивание весов или ревизий, которых нет в этом файле, требует решения владельца.

## 10. Изменение направления: единый плагин записи и анализа
