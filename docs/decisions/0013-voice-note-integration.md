# 0013. Единый плагин: запись Voice Note и асинхронный анализ Sound Scout

- **Статус:** принято направление по поручению владельца от 19–20 ноября 2026 года; отдельные
  пункты ждут решений владельца (раздел 9).
- **Источники:** приватное поручение владельца (не в git), исходники Hermes Agent v0.23.1
  (`3b4215785882`) и его документация, репозиторий `renidere/hermes-voice-note` (v0.4.2, `ced69ea`)
  и его аудит, код Sound Scout на `1fce028`. Исследование — только чтение; два независимых проверяющих
  сверили выводы с исходниками.
- **Заменяет:** `docs/spec/REQUIREMENTS.md` §2 (запреты кнопки записи, сервиса загрузки, очереди и
  фонового исполнения) и часть R12 «без Desktop plugin». ТЗ меняет только владелец: пометки в
  `docs/spec/` и раздел 10 ТЗ вносятся его шагом в #93; до этого действует это решение.

## 1. Цель

Один продукт для одного сценария: **записать в нужном чате → отправить → при необходимости запустить
анализ → получить результаты по готовности → открыть отчёт и сравнить контрольный дубль.**
Основной репозиторий — `sound-scout-plugin`. Voice Note даёт рекордер, Sound Scout — анализ.

## 2. Как всё запуталось (факты)

1. Voice Note v0.2–v0.3.2 работал на штатных вызовах SDK: `profileRoutes`, `retainProfile`,
   `requestProfile`, `file.attach`, `composer.submit`. v0.3.2 отказывал в отправке, когда публичный
   `focusedSessionOwner` возвращал `null`. Тест «устаревший null или owner действительно неизвестен»
   так и не запустили.
2. v0.4.0 закрыл пробел новым методом SDK `host.retainSession` и сделал его обязательным в
   `register()`. Плагин перестал работать в любом штатном клиенте.
3. v0.4.1–0.4.2 доставляли этот SDK собранным неподписанным Windows EXE со своими `HERMES_HOME` и
   `userData`, то есть вторым клиентом и профилем. `plugin.js` между 0.4.0 и 0.4.2 не менялся.
4. Тот же патч лежит незакоммиченным в `~/.hermes/hermes-agent` вместе с правкой документации.
   Поэтому локальная документация показывает `retainSession` как штатный контракт; это не так.
5. Windows CI проходил на побочных ветках, в изолированных профилях, без микрофона и backend. В
   receipt релиза `actualUserDeliveryVerified: false`: доставку в настоящий чат никто не проверял.
6. ТЗ Sound Scout v1 запрещало плагин, загрузку и очередь. Sound Scout честно построен как
   синхронный stdio-инструмент, и у двух проектов не было общего контракта.

Общий рисунок: недоказанная причина принята за доказанную, решение расширило платформу вместо
использования её контрактов, приёмка опиралась на изолированные заменители.

## 3. Решения

### 3.1. Клиенты равноправны

Ядро анализа не привязано к Hermes. Одна очередь заданий доступна через три входа с одной
семантикой и одними правами:

- **CLI** `sound-scout jobs submit|status|result|cancel|retry|recover` — для любого агента и
  оператора;
- **MCP** — асинхронные инструменты в существующем сервере `speech-review` (рядом с
  `speech_capabilities`, `speech_compare` и синхронным `speech_analyze`, который сохраняется для
  совместимости и eval);
- **плагин Hermes Desktop** — клиент поверх того же контракта.

Смена агента (Hermes, Claude Code, Codex) не требует нового кода анализа.

### 3.2. Пакет плагина

Один unified package Hermes в репозитории (`hermes/plugin/sound-scout/`):

- `desktop/plugin.js` — один ESM-файл для штатного Hermes Desktop на Windows, установка через
  «Install from Git» (Desktop target, подкаталог репозитория поддерживается кодом установщика;
  на Windows не проверено);
- `dashboard/plugin_api.py` — маршруты `/api/plugins/sound-scout/` в процессе gateway на Linux;
  включается владельцем через `plugins.enabled` и перезапуск gateway.

Отдельный EXE, форк Hermes, второй профиль и второй клиент не нужны и не допускаются.

### 3.3. Рекордер

Переносится из Voice Note v0.4.2: захват `getUserMedia` с выключенной DSP браузера, WAV PCM16,
отмена через счётчик поколений, сохранение WAV при сбое шага, тестовый harness. `host.retainSession`
заменяется штатным путём v0.3.x: `profileRoutes` по захваченному owner → `retainProfile` →
`session.resume` → `file.attach`. Чат адресуется `focusedStoredSessionId` и копией
`focusedSessionOwner`, захваченными в момент начала записи; название чата — не идентификатор.
Owner `null` перечитывается при отправке; отказ — только при неоднозначном маршруте.

Лимит длительности клиента равен бюджету сервера (сейчас 180 с, а не 300 с Voice Note); сервер
отдаёт бюджеты через `GET /health`.

Черновик WAV хранится в IndexedDB рендерера до серверного receipt (`ctx.files` пишет только текст
до 4 MiB).

### 3.4. Отправка

Обычная отправка не запускает анализ. Штатный `composer.submit` может вернуть ложное подтверждение
и не работает для скрытого чата. Spike A выбирает: `prompt.submit` с `submission_id` через
`requestProfile` (durable admission) либо `composer.submit` с проверкой чтением. При повторе после
сбоя только отправки используется уже полученный результат `file.attach`, без второй копии файла.

### 3.5. Приём на анализ

«Отправить и разобрать» загружает WAV в `plugin_api` через `ctx.rest` (JSON `data_url`) прямо в
приватный staging-корень Sound Scout (0700, вне `~/.hermes`, один из `allowed_roots`). Правило корней
#66 не меняется. Чтение файлов из `~/.hermes/attachments` по пути из `file.attach` — только по
отдельному решению владельца (раздел 9, пункт 2), и тогда по абсолютному полю `path`, не по
`ref_path`.

Правка 2026-11-23 (#168, [Decision](https://github.com/renidere/sound-scout-plugin/issues/168#issuecomment-7099897317)).
Desktop 0.23.3 при входе паролем (`basic`) шлёт `ctx.rest` через cookie-ветку. Эта ветка отказывает
любому `upload`. Поэтому WAV идёт одним JSON-телом `POST /jobs` `{"data_url":
"data:audio/wav;base64,…"}`, той же строкой, что и `file.attach`. Приём multipart удалён: путь один.
`plugin_api` читает тело с потолком из `max_input_bytes` (base64 плюс префикс и 1 KiB на JSON). До
создания файла он проверяет `Content-Type`, размер, форму JSON и base64. Отказ — `bad_request`,
`bad_base64`, `empty_upload` или `input_too_large`, на диске ничего не остаётся. Затем `<uuid4>.upload`
с `O_EXCL|O_NOFOLLOW` и `jobs submit`, как раньше. Чанков нет. Если живая проверка упрётся в размер
тела, чанки станут отдельной задачей.

Копирование, SHA-256 и вызов CLI выполняются вне event loop gateway (`asyncio.to_thread`).

### 3.6. Задания на сервере

Новый модуль `src/sound_scout/jobs.py`, хранилище — файлы `<data_root>/jobs/<job_id>/`: `job.json`
(запрос, зафиксированный план, привязка, состояние), попытки, маркер отмены, маркер доставки.
Индекс `request_id` устроен как `runs.open_run`: hash идентичности, публикация жёсткой ссылкой,
`RequestMismatch` при конфликте. Идентичность задания = SHA-256 входа + план + привязка; идентичность
run в `runs.py` не меняется.

- `submit` пишет задание и отвечает `job_id` меньше чем за секунду; проверка входа — первая
  асинхронная стадия.
- **Runner** — один процесс, singleton по своему `runner.lock` (не `analyze.lock`). Он берёт
  задания FIFO и вызывает `app.analyze` без изменений; `analyze.lock` берёт сам `app.analyze`. `Busy`
  (например, от синхронного MCP-вызова) возвращает задание в очередь.
- Runner запускается вне cgroup gateway: `systemd-run --user` transient unit с фиксированным
  именем. Причина: unit gateway имеет `KillMode=mixed`, а worker — `die_with_parent`; дочерний
  процесс gateway погибает при каждом перезапуске.
- Отмена между процессами — маркер в каталоге задания; наблюдатель в runner переводит его в
  существующий `CancelToken`.
- Каждая попытка получает свой `request_id` run (`<job>-a<n>`), поэтому `run_incomplete` не
  блокирует повтор. Повторный анализ того же аудио из другого чата выполняется заново: run
  переиспользуется только по повторному `request_id`.
- Lease попытки (boot_id, pid, время старта, номер) позволяет `jobs recover` пометить прерванную
  попытку и поставить видимую новую, без скрытых повторов.
- Состояние задания (`queued/running/finished/cancelled/failed`) отделено от `result.status`
  (`complete/partial/failed`) и от охвата функций. «Задание закончилось» не означает «всё
  запрошенное выполнено».
- Маркер `work/stage-current.json` показывает идущую стадию; готовые стадии — из
  `work/stage-*.json`.
- Режимы `quick/targeted/full/auto` разрешаются в план стадий, который сохраняется в `job.json`.
  План может только сужать бюджеты оператора, но не расширяет корни, сеть, лимиты или backend.
- Задание из MCP создаётся без привязки; привязку к локальному чату ставит плагин через
  `sound-scout jobs bind` — решение 0025 (`docs/decisions/0025-mcp-chat-binding.md`).

### 3.7. Доставка в чат

Один итог на задание. Внутри gateway есть `gateway.session_cron.deliver_to_local_chat`: пишет
заметку в историю без вызова модели и восстанавливает закрытый чат. Это внутренняя функция; она
работает только в процессе, который владеет session authority (`plugins.isolation: in_process`), и
блокирует до 60 с, поэтому вызывается из отдельного потока. Её использование — решение владельца
(раздел 9, пункт 3). Запасные пути: cron-задание со скриптом и локальной доставкой либо
`ctx.inject_message` (стоит хода агента и требует `allow_gateway_injection`).

Hermes не дедуплицирует такие заметки. Поэтому доставка **не более одного раза**: маркер пишется до
вызова; при таймауте история чата проверяется по метке задания, и без неё задание получает статус
`delivery_unconfirmed` с ручной повторной доставкой, без слепого повтора. Фоновая доставка работает
только в процессе-владельце сессий: на станции три процесса Hermes делят один `config.yaml`.
Владелец сессий на станции — `hermes gateway run` (`hermes-gateway.service`), не `hermes serve`;
см. 0017.

Карточка отчёта через директиву `::sound-scout-report{...}` в заметке не доказана: заметки cron
хранятся как `internal_notification`. Spike B это проверяет; запасной путь — простой текст в
заметке и карточка через опрос `GET /jobs/<id>`.

Правка 2026-11-23 (#108, [Decision](https://github.com/renidere/sound-scout-plugin/issues/108#issuecomment-7108195290)).
Директива `sound-scout-report` удалена из Desktop-плагина: заметка идёт простым текстом (запасной
путь). Карточка задания живёт в `COMPOSER_AREAS.top` того чата, где записан голос. Её данные — тот
же последовательный опрос `GET /jobs/{job_id}` раз в 3 с: этапы плана, `finished_stages`,
`current_stage`. Сообщений в чат на этап нет. Полный отчёт — `GET /jobs/{job_id}/report`
(`sound-scout jobs report`, до 256 KiB), простой текст в SDK `Dialog`, без Markdown. Обрезанный
отчёт называет полный файл: `<run_dir>/report.md` в data root. Отмена и повтор — `POST
/jobs/{job_id}/cancel` и `POST /jobs/{job_id}/retry`; повтор сохраняет `job_id`. После отказа
повтора карточка один раз запрашивает статус; не ответил и он — кнопка «Обновить».

### 3.8. Агентский путь

Агент запрашивает анализ через MCP-инструменты заданий. При обычной отправке голосового агент
**не** запускает синхронный `speech_analyze` сам: это меняет skill `speech-review` уже в
минимальном сквозном пути, иначе он конкурирует с runner за `analyze.lock` и дублирует анализ.

Содержательный разбор упражнений (главная мысль, факт/версия, ответ собеседнику) делает агент по
транскрипту. Слой `content` Sound Scout — только ASR, не анализ дискурса.

## 5. Минимальный сквозной путь (сначала только он)

**Порядок этапов (решение владельца 20 ноября 2026):** сначала Linux-часть работает самостоятельно —
очередь заданий, runner, CLI и MCP, backend-маршруты, доставка итога в чат Hermes; проверка —
[#114](https://github.com/renidere/sound-scout-plugin/issues/114). Windows-клиент (рекордер,
Spike A, сквозной путь владельца) — отдельный эпик
[#115](https://github.com/renidere/sound-scout-plugin/issues/115), он стартует после #114.
Шаги ниже сохраняют полный путь; шаги 2, 6 и 7 относятся к этапу Windows.

1. Владелец утверждает это решение и решения раздела 9.
2. **Spike A** (диагностический плагин на настоящем Windows Desktop): stored id, owner,
   `profileRoutes` для старого, переименованного и нового чата; путь `desktop-plugins`; загрузка
   синтетического WAV 30 с через `retainProfile → session.resume → file.attach` со сверкой SHA-256 на
   backend; настоящий ли ACK у `prompt.submit` и `composer.submit` при скрытом чате.
3. **Spike B** (пакет-заглушка на backend): `GET /health` через `ctx.rest` с Windows; доставка
   заметки в открытый и закрытый чат ровно один раз; отображение директивы в заметке; запуск
   `systemd-run --user` из процесса gateway.
4. Ядро заданий: `jobs submit/status/result/cancel`, хранилище, runner, режим `quick`
   (prepare + acoustics + ASR; `audio_review` честно `unavailable`); тесты на синтетике.
5. `plugin_api`: `POST /jobs` (JSON `data_url` в staging, правка #168), `GET /jobs/<id>`, `GET /health`, доставка.
6. Desktop: рекордер на штатных вызовах, «Отправить» и «Отправить и разобрать», прогресс текстом.
7. Владелец на Windows: запись в чате X, переключение на чат Y и переименование X во время
   анализа, закрытие Desktop; после открытия в чате X есть голосовое и ровно одна заметка с
   итогом, `report.md` сохранён, в чат Y ничего не пришло.

Только после шага 7: отмена и повтор в UI, режимы, маркер текущей стадии, карточка, черновик в
IndexedDB, MCP-инструменты заданий, контрольные попытки, доступность.

## 6. Ресурсы

Тяжёлый inference последователен (один runner). Admission при `submit`: максимум заданий в очереди и
байт в staging; отказ с понятной причиной. Ожидание в очереди и deadline стадии считаются отдельно;
таймаут клиента не теряет принятое задание. Staging-копия удаляется после доставки и срока хранения
из конфигурации оператора.

## 7. Что сохраняется

Синхронные `speech_analyze`, `speech_compare`, CLI `analyze`/`compare`, контракт результата 1.2,
правило корней #66, сетевой запрет, лимиты R02/R10/R11, отсутствие Redis/Celery/новых портов.

## 8. Приёмка

Сценарии A01–A14 из поручения владельца — отдельная задача владельца на настоящем Windows-клиенте.
Unit-тесты и моки не заменяют её; мок модели не доказывает слух.

## 9. Решения владельца

1. **Локальный патч Hermes.** `~/.hermes/hermes-agent` содержит незакоммиченные `retainSession` и
   правку `composer.submit`. План на них не опирается. Откатить или оставить?
2. **Анализ уже приложенной записи по просьбе агента.** Разрешить ли `plugin_api` читать файл из
   `<profile>/attachments` (только абсолютный `path`, обычный файл без symlink, в бюджете) и
   копировать в staging? Это обходит смысл решения A (#66), хотя guard не меняется. По умолчанию —
   нет: анализ только для записей, загруженных через «Отправить и разобрать».
3. **Доставка во внутреннюю функцию gateway** `deliver_to_local_chat` (без вызова модели) или запасной
   путь `ctx.inject_message` (ход агента).
4. **Репозиторий Voice Note.** Пометить README, Windows-клиент и релизы 0.4.1–0.4.2 как
   устаревшее направление; удаление — отдельно после проверки замены.
5. **Процесс-владелец чатов Desktop.** Подтвердить, что это `hermes-autonomous.service`, и включить
   пакет с `plugins.isolation: in_process` для профиля `default`.
   Установлено агентом: посылка неверна, владелец — `hermes-gateway.service`; см. 0017.
