## 1. Цель

Тот же протокол Gate 0, что в локальных прогонах `0023` и `0024`, в официальном runtime и в bf16.
Прогон показывает, что скрывают квантование (Q4_K_M, Q8_0) и маршрут аудио llama.cpp
(дополнение до 30 с, `0024` § 2.2). Вердикт каждой модели выводит код по правилу её локального
прогона. Сравнение с локальными вердиктами — по каждому критерию (раздел 6).

GPU-вердикт не заменяет локальный и не меняет `backend`. `READY` здесь — вердикт эталона, а не
решение о подключении: подключение — #90 по решению владельца.

## 2. Пакет и порядок шагов

Один инстанс. Один create без повтора. Шаги `deploy`: `arm`, `create`, `ready`, `preflight`,
`weights` (обе модели), затем для каждой модели по порядку `smoke` и `run`, затем `download` и
`destroy`.

- **Порядок моделей:** сначала Qwen2.5-Omni-7B, затем Qwen3-Omni-30B-A3B-Instruct. Путь
  Qwen2.5-Omni прошёл `smoke` в попытке 5 пилота #148. Если упадёт вторая модель, результат
  первой уже на станции.
- **Свежий сервер на модель.** У каждой модели свой `hostrun.py serve` с её `rss_limit_bytes` и свой
  `vllm serve`. После `run` стек пишет в журнал улики хоста (`server_evidence`: хвосты логов,
  `server-stats.jsonl`, процессы) и останавливает сервер (`server_stopped`). `hostrun.py stop`
  считает сервер остановленным, только когда нет ни `serve`, ни живого процесса сессии сервера
  (её id — строка `started` в `server-stats.jsonl`). Если сервер не остановился, следующая
  модель не стартует, и стек удаляет инстанс.
- **Своё правило на модель.** До `opened` (до любой записи журнала и вызова API) `vast.check_days`
  проверяет: день Gate 0 подготовлен; блок правила в документе решения модели — правило её
  локального прогона (`vast.GATE0_RUNS`); манифест дня записан под тем же блоком; набор клипов
  дня — ровно `clips` из пакета (id и SHA-256 каждого WAV на диске), и день не `--controls-only`.
- **Любой сбой** шага ведёт к destroy и проверке отсутствия (`0026` § 4). Вердикт NOT READY — не
  сбой: вторая модель идёт и после него.

Формат пакета — тот же, что у `0027`, с двумя записями в `models`. Новое — необязательное поле
записи `clips` (`{id: SHA-256 WAV}`); `vast.load_package` проверяет его, потолок
`rss_limit_bytes` модели и диск (раздел 5).

### 3.1. Кэши vLLM (находка #148)

vLLM принимает поле `cache_prompt` без ошибки, но кэш оно не выключает. По умолчанию у vLLM
включены prefix caching и кэш мультимодального препроцессора. Пилот #148 (раздел результатов
`0027`): попадания prefix cache 18–24 %, кэша мультимодальных входов 44–55 % по логу сервера; K2 на
каждом контроле шёл в 1,9–2,1 раза быстрее K1 при том же числе токенов (`trace.jsonl` попытки 5).
K2 и A на одном клипе были не холодными. Локальные прогоны шли с `cache_prompt: false` в
`llama-server`, то есть холодными.

**Выбор (#161): кэши выключены флагами, которые есть в vLLM 0.34.0, а поле `cache_prompt` vLLM
не получает.** `--no-enable-prefix-caching`
(флаг `BooleanOptionalAction` поля `CacheConfig.enable_prefix_caching`) и
`--mm-processor-cache-gb 0` (поле `MultiModalConfig.mm_processor_cache_gb`, «0 — кэш выключен»).
Оба флага проверены по исходникам тега `v0.34.0` (`vllm/engine/arg_utils.py`,
`vllm/config/cache.py`, `vllm/config/multimodal.py`). Флаги действуют на все пакеты стека.

**Остаётся известным отличием:** кэш выходов аудиоэнкодера по `mm_hash`
(`vllm/v1/core/encoder_cache_manager.py`) держит освобождённые записи до вытеснения и флага
выключения не имеет. Повтор одного клипа может не пересчитывать энкодер. Это меняет время
запроса; выход энкодера — та же функция того же входа. Секунды на запрос сравниваются с
локальными только с этой оговоркой.

## 5. Ограничения

- Один инстанс on-demand. Одна попытка: create один раз, без повтора и без запасного offer.
- Перезапусков сервера внутри модели нет. Провал `smoke` модели — её `run` не идёт, затем destroy.
- 42 запроса на модель, каждый один раз. Таймаут клиента — 600 с. Клип ≤ 30 с.
- RSS дерева сервера ≤ `rss_limit_bytes` модели (раздел 3); VRAM пишется отдельно.
- **Диск — 110 GB.** `vast.load_package` требует веса всех моделей пакета плюс запас 10e9,
  округлённые вверх до 10 GB: 92 909 633 353 + 10 000 000 000 → 110 GB. В пилоте диск 80 GB дал
  85 868 453 888 свободных байт: образ в этот объём не входит.
- На хост загружаются только закреплённый образ и два репозитория на закреплённых ревизиях.
- Без volumes, snapshots, interruptible, reserved, serverless и пополнения баланса.
- SSH-ключ попытки — только на инстанс, не на аккаунт.

## 6. Что сравнивается с локальными вердиктами

Для каждой модели — её GPU-попытка против её локальной попытки, по каждому пункту правила:

| Критерий | Qwen2.5-Omni-7B, локально (`0024`, попытка 3 дня 2026-11-19) | Qwen3-Omni, локально (`0023`, попытка 2 дня 2026-11-21) |
|---|---|---|
| Вердикт | NOT READY | NOT READY |
| P1 (E0 до вызова) | выполнено | выполнено |
| P2 (веса, промпт A) | выполнено (GGUF Q8_0 и mmproj f16) | выполнено (GGUF Q4_K_M и mmproj Q8_0) |
| P3 (аудиомаршрут) | выполнено по построению: дополнение до 30 с, 750 позиций на любой клип | выполнено по v2 |
| C1 (K1, K2 на `S0`, `N1`, `T1`) | 6 из 6 | 6 из 6 |
| C2 (P на контролях) | 1 из 3: `да` на `S0` и `N1` | 1 из 3: invalid на `S0`, `length` на `T1` |
| C3 (A на контролях) | 0 из 3: выдуманное наблюдение о произношении | 3 из 3 |
| C всего | 7 из 12 | 10 из 12 |
| S (синтетические пары) | 0 из 3 | 0 из 3 (пустые P на `V1–V3`) |

Для каждой модели результат даёт:

1. Вердикт GPU и причину (`python -m sound_scout.eval.gate0 verdict --date <день> --attempt <k>`).
2. Каждый из 12 пунктов C и каждую пару S: GPU против локального, совпадение или отличие.
3. P3: аудиотокены на секунду клипа по каждому audio-запросу. По `0022` § 3.1 эталон transformers не
   дополняет вход до 30 с; ожидание — число аудиотокенов растёт с длительностью. Это ожидание, а
   не факт до прогона.
4. Ответы A на речевых клипах и transcript-only ответы — в вердикт не входят; публикуются без
   личного содержимого, как в `0023` и `0024`.
5. Секунды на запрос и пиковые VRAM и RSS — с оговоркой раздела 3.1.

**Отличия условий, известные до прогона:** dtype (bf16 против Q8_0 и Q4_K_M); runtime (vLLM 0.34.0
против `llama-server` b12359); маршрут аудио (процессор transformers против дополнения до 30 с);
шаблон чата (`chat_template.json` модели против шаблона GGUF); `--max-model-len 8192` против
`-c 4096`; кэш энкодера vLLM (раздел 3.1); P2 — квитанция хоста, а не файлы станции. Причину
отличия вердиктов прогон не доказывает: он показывает, совпадают ли пункты при этих отличиях.

## 7. Деньги и сроки

Формула стека (`vast.estimate_usd`): `dph_total × часы + входящие GB × inet_down_cost + исходящие
GB × inet_up_cost`. Входящий трафик — 102,95 GB (образ 10,037 + веса 92,910 + клипы < 0,01).
Исходящий — ≤ 1 GB. Оценка считается на дедлайн всего пакета (60 мин), то есть на обе модели.

- **Потолок пакета — 1,20 USD**: compute, storage, трафик, лаг биллинга, удаление. Стек отказывает
  в create, если оценка на дедлайне выше потолка. При ценах трафика пилота (0,0026042 и
  0,0039063 $/GB) трафик — 0,272 USD; тогда `dph_total` котировки — не выше 0,928 $/ч.
- **Ранний порог — 0,90 USD** наблюдаемого расхода (75 % потолка; начальный кредит − текущий).
- **Дедлайн — 60 мин от `opened`.** Абсолютное UTC-время пишется в журнал и в таймер `cutoff`.

| **Всего** | **≈ 27** | дедлайн 60 мин |

## 8. Сторож

Как `0027` § 8, с порогом этого пакета. Два таймера `systemd-run --user` до create:

- `sound-scout-gpu-<attempt>-watch` — тик раз в 60 с. Destroy всех инстансов попытки: дедлайн;
  исход create неизвестен; больше одного инстанса с меткой; пульс агента старше 300 с; запрошен
  destroy; наблюдаемый расход ≥ 0,90 USD.
- `sound-scout-gpu-<attempt>-cutoff` — на дедлайн и на дедлайн + 15 мин: безусловный destroy,
  затем поиск потерянного create по метке.
- На хосте: `onstart` завершает PID 1 через дедлайн + 300 с; `hostrun.py serve` останавливает vLLM
  на дедлайне.

Удаление при завершении, ошибке, отмене и лимите разрешено владельцем заранее (7083719621).

## 9. Удаление и проверка

1. `download`: архив с хоста, SHA-256 архива и каждого файла по `SHA256SUMS`. Destroy идёт и при
   отказе сверки.
2. `DELETE /api/v0/instances/<id>/` для каждого id попытки. Stop не используется.
3. Отсутствие: в `GET /api/v1/instances/` с фильтром по метке нет id, и `GET /api/v0/instances/<id>/`
   не отдаёт инстанс. Затем `absence_verified`, `closed`, таймеры остановлены.
4. После `closed` исполнитель читает полный список инстансов аккаунта (`vast.Api.instances()` без
   метки). Он должен быть пуст; ответ пишется в результат.
5. Кредит: сразу после `closed` и через 24 ч. Дельта ≤ 1,20 USD.

## 10. Данные владельца

- `B1–B3`, `V1–V3`, расшифровки и целевые слова уходят только в запросах Gate 0 клиента к vLLM
  инстанса этой задачи, через SSH-туннель. На хост файлы клипов не копируются: туда идут только
  `hostrun.py`, guard и `models.json`.
- vLLM 0.34.0 не пишет запросы в лог: `--enable-log-requests` по умолчанию выключен, стек его не
  включает. Логи и `server-stats.jsonl` хоста возвращаются на станцию архивом и уничтожаются на
  хосте вместе с инстансом (`destroy`).
- Ответы модели, `trace.jsonl`, `run.json` и `verdict.json` лежат в каталогах дней на станции,
  вне git. В результат идут хеши, числа и выдержки без личного содержимого.
- Другие записи владельца, held-out и публикация этим согласием не разрешены. Риск доступа
  оператора хоста к файлам владелец принял (7065928031).
